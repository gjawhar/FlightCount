"Flights before Flight Counter" is v1's "Starting Lifetime Count", renamed so it's clear what it's for. Changing it later just adds a new line (the latest value wins), so it shifts Lifetime and nothing else. A v1 upgrade fills it in for you. Undo removes an accidental count (asks first, shows which flight). Erase asks twice. Neither deletes lines from the log: they add a correction line, so even these can be reversed by hand if needed.

5. How the data is kept

One line per flight, appended to Files/flights.csv. Totals, today, month and year are added up from the lines once at power-up, then kept in memory. Appending never rewrites what's already there, so a glitch can at worst lose the one line being written, never the history.

time,date,model,n,kind
1758901234,2026-09-26,M3,1,flight        one flight
1758904100,2026-09-26,M3,-1,undo         undo of an accidental count
1758000000,2026-09-15,M3,150,before      "Flights before Flight Counter" (latest line wins)

Files/models.csv maps a model key (M3) to the model's file, its receiver ID and its current name. Ethos names the file after the model (DLG V220X NEW → dlg v220x new.bin) and renames it when you rename the model, so the file alone isn't enough: see "Model renamed" below. Size: about 40 bytes a flight, so 10 flights a weekend for 10 years is roughly 200 KB — adding it up at power-up takes a moment, not seconds. Your old v1 files are read once and left exactly where they are, as a backup.

6. Edge cases — decided in this draft

CaseWhat 2.0 does
Storage glitch at bootShows "– –" and retries every second. Never shows or saves 0 over real data. (This is the likely cause of the field report: in v1 one failed read at power-up turned 250 flights into 1.)
Model renamedEthos renames the model's file too (verified on 1.6.7). The widget sees a new file name, checks the models folder, finds that a model it knew has vanished and had the same receiver ID or name, and carries its counts over. Name on screen updates.
Model cloned for a new airplaneDECIDED (you clone all the time). New file, and the original's file is still there → a clone, starts at 0. Works on 1.6, where the clone copies the receiver ID, and on 26, where it usually doesn't.
Can't find the models folderIf the widget can't locate the current model's own file (unusual storage setup), it never guesses: a new file name simply starts fresh, so two airplanes can't get merged.
Receiver re-boundNo effect on counts (same file).
Model restored from a backupSame file name as before → same counts.
Two Flight Counter widgets on one model(e.g. a small tile on page 1, the chart on page 2.) Both show the same numbers. Set the trigger on one of them; if more than one has a trigger set and they fire together, the flight is still logged once, not once per widget.
Model switched without power cycleRe-checks the model every wakeup and swaps to that model's counts.
"Today" / month / yearCalendar day/month/year on the radio clock. If the radio clock is wrong, dates are wrong too (the count itself is fine).
Power off during the delayNothing logged (same as v1).
Trigger held on at power-upDECIDED: does not count until the switch has been seen OFF once. (v1 counted immediately.)
Upgrade from v1One-time import per model: v1 lifetime minus today, plus v1's starting count, becomes Flights before Flight Counter; v1's today becomes dated flights today. v1 files untouched. Never imports twice: a v1 name is claimed by the first model that boots with it, so a clone made later with the same name does not pick up the original's v1 counts.
Reinstall over an existing installGoal: the release ZIP ships no Files/ folder, so an installer has nothing to replace it with, and the widget creates the folder itself. Ethos documents os.mkdir(); I'll confirm it works on 1.6 and 26 before relying on it. Either way, your flights are in the append-only log.
Ethos 1.6 and 26Must run on both (you're staying on 1.6.x). Tested in the 1.6.7 and 26.1.2 X20RS simulators before release.
